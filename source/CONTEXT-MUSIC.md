# 上下文点歌（共同源码 v1.39）

2026-11-09：聊天发送入口现在实际调用上下文解析。GPT 与 DeepSeek 使用同一套流程、各自的配置和 API；正式发行目录及 GitHub 发布包未同步。

## 试用

项目根目录的 `老八.lnk` 和 `老八-DeepSeek.lnk` 现在分别指向 `杏菜桌宠/build/GPT` 和 `杏菜桌宠/build/DeepSeek` 的共同源码构建。聊天窗口标题与初始状态应显示 **v1.39**。已有实例时，新启动程序会提示先退出，避免旧版仍在运行而误认为已更新。`开源发布` 及独立发行目录仍保持原状，不用于验证本次修改。

1. 在设置中填写所选服务的 API Key。
2. 说“推荐一首日语歌给我”。
3. 杏菜推荐后，说“可以，那你开始播放吧”。
4. 有多个版本时按实际候选回答，例如“第二个版本”。
5. 以“操作结果”气泡为准：找到候选、发出播放请求、确认正在播放、失败是不同结果。客户端登录及歌曲播放权限仍由 QQ 音乐决定。

## 实现边界

- `MusicConversation` 将最近最多 20 条消息（含音乐回执）、较早对话摘要/相关原文、当前有效候选和本次输入交给当前模型，解析为 `chat/play/choose/control/clarify`。历史背景不是当前候选或当前播放状态。
- JSON 严格校验字段及类型；格式错误只允许模型修正一次，仍无效则停止，不用旧关键词猜歌作为回退。认证/网络失败不进入格式修正，也不重复已执行的音乐操作。候选带程序生成的版本号，过期选项不能继续执行。
- 区分对话推荐和 QQ 搜索候选：对澄清问题回答“前一首吧”，应解析为上文歌曲的搜索请求；只有已有 QQ 候选时才按候选编号选歌。
- `MusicRouter` 只执行受支持的搜索、选择和控制操作，模型不能提交任意程序命令。歌曲查询单独进入搜索，不再经过口语正则裁剪。
- 实际工具结果会返回模型供角色回复使用，同时在界面保留原始回执。回复生成失败不会重试播放操作；停止回复不代表撤销已发送的音乐请求。
- 无 Key 时保留已有明确命令、本地播放与记忆管理。具备 Key 的上下文点歌会调用模型：普通聊天通常为解析、回复各一次，音乐操作另含结果回复；意图格式错误时最多额外修正一次，按各服务正常计费。
- 本地构建附带 `MusicSession.ps1`、三套服装和音色服务启动文件。音色引擎、模型及第三方客户端仍需本机具备。

## 验证

在项目根目录运行：

```powershell
& '.\杏菜桌宠\source\run-context-tests.ps1'
```

通过真实聊天窗口发送方法、HTTP 模拟响应及 QQ 模拟接口，验证推荐确认、候选选择、普通/否定聊天、歧义澄清、无效 JSON、取消、过期列表、回复失败不重放及日语配音。此测试不读取真实密钥、不调用网络、不播放歌曲。

可选实网解析检查（会使用设置中保存的 API Key，每服务四个合成案例；不播放歌曲）：

```powershell
& '.\杏菜桌宠\source\run-live-music-tests.ps1' -RunLive
```

本次离线集成测试：GPT 217 项、DeepSeek 216 项断言通过，包括澄清后选歌、格式修正限次、候选修正不重复搜索、认证失败与取消不重试。现有 GPT 后端 72 项断言及两版完整桌宠自检通过。在用户环境使用原有配置实测，DeepSeek 四个解析案例全部通过，新增截图案例（推荐 Official髭男dism《Pretender》后追问偏好，用户说“放给我听听”）也正确解析为 `play`，查询为 `Official髭男dism Pretender`；两首推荐经澄清后回答“前一首吧”解析为 `play` 和 `YOASOBI 夜に駆ける`。GPT 的保存密钥被接口拒绝，未能完成实网验证。沙箱的用户配置目录与真实用户目录隔离，因此实网检查需要在用户环境运行。未验证 QQ 音乐实际出声；少量解析案例也不能证明所有自然语言的线上识别准确率。
